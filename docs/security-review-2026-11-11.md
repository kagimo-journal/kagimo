## High
- **H1. The second factor is not enforced on passphrase sign-in for passkey-only accounts, or at all for the bootstrap admin.**
  - Where: `auth_handlers.go:86` only requires a second step when TOTP is enabled. `withSession` accessActive/accessAdmin never check `hasSecondFactor`.
  - Fix: when the account has passkeys but no TOTP, passphrase sign-in creates an `mfa_pending` session that must be completed by a passkey assertion for that user (allowCredentials = the user's credentials, UV required). Refuse active/admin access to users without a second factor (bootstrap admin and `approve -force`) until they finish setup.
  - **Outcome: FIXED (backend).** `POST /api/auth/login` now answers `totp_required` (TOTP only), `totp_required` + `passkeyAllowed:true` (TOTP and passkeys) or `passkey_required` (passkeys only) with an `mfa_pending` session; new `POST /api/auth/login/passkey/begin|finish` (allowCredentials = the user's credentials, UV required, challenge bound to the session user, assertion validated against that user's credentials only, failures count toward the 5-per-session cap, session rotated on success). `withSession` refuses `accessActive`/`accessAdmin` with `403 second_factor_required` for accounts without TOTP or a passkey (bootstrap admin, `approve -force`); they keep the "any status" endpoints. Contract in SPEC §5 / §5.1 ("Passphrase sign-in", "Second factor"). Tests: `TestPassphraseLoginRequiresPasskeyStep`, `TestPasskeyStepFailuresDiscardSession`, `TestPassphraseLoginEitherSecondFactor`, `TestSecondFactorRequiredForActiveAccess`, e2e step "without a second factor…". **Frontend: FIXED.** Sign-in shows the passkey step for `passkey_required`, offers either factor for `totp_required` + `passkeyAllowed` (`/login/passkey/begin|finish`, UV required), explains `totp_locked` with `lockedUntil`, and restarts on an expired/discarded `mfa_pending` session. Users with `status == "active" && !hasSecondFactor` are routed to `/signup/secure` with an explanation and no longer call `/api/settings` (or any journal endpoint) first; any `403 second_factor_required` re-reads `/api/me` and routes there. Checked in a headless-Chromium run with a virtual authenticator (passkey-only account → passphrase → passkey step → journal).

## Medium
- **M1. Unauthenticated memory exhaustion.** Unvalidated usernames of up to 1 MB become rate-limiter map keys (prelogin/login/recover). Fix: validate or normalise the username, or hash it, before it reaches the limiter; cap its length.
  - **Outcome: FIXED.** `loginUsername` trims/lower-cases and validates before any limiter or map; raw input > 64 bytes or not `[a-z0-9._-]{3,32}` maps to the fixed key `!invalid` (prelogin, login, recover/verify). Test: `TestHugeUsernameDoesNotBecomeAKey` (1 MB username; asserts no limiter key > 128 bytes).
- **M2. Anyone who knows a username can block passphrase sign-in for it, and the lockout reveals that the account exists.** One wrong guess every 2 minutes keeps it locked; existing accounts answer 429 while unknown ones answer 401. Fix: a long-lived signed device cookie gets its own counter and is exempt from the account-wide lock; unknown usernames keep the same failure counter so they behave identically.
  - **Outcome: FIXED.** Signed device cookie `jdev` (HttpOnly, SameSite=Strict, Secure on https, Path=/api/, 1 year; HMAC-SHA256 over user id + device id + expiry with an HKDF subkey of secret.key) set on every full sign-in and sign-up. Wrong passphrases (login, reauth, passphrase change) are charged to a per-(user, device) bucket (10/h) when the request carries a valid cookie for that user, otherwise to the account bucket (30/h, keyed by username); the account lock does not apply to recognised devices. Unknown well-formed usernames use the same account bucket, so their 401/429 sequence and hashing work are identical. Tests: `TestAccountLockDoesNotBlockRecognisedDevice`, `TestUnknownUsernameIndistinguishable`.
- **M3. The passphrase policy accepts word + year passwords** such as `Summer2024!!` and `Liverpool2023` (`frontend/src/lib/strength.ts`). Fix: zxcvbn-style dictionary/pattern estimation, or a floor of 4+ words or 16+ characters.
  - **Outcome: FIXED (frontend).** `src/lib/strength.ts` is now a zxcvbn-style estimator: letter/digit/symbol runs are matched against compact common-password, English-word and name lists (derived from zxcvbn 4.4.2's MIT-licensed frequency lists, a lazily loaded ~150 KB / ~70 KB gzipped chunk used only by the sign-up, change-passphrase and recovery-reset fields), years, dates, repeats, sequences and l33t substitutions; whole-string matches of known passwords are capped low and the username is refused. Policy: ≥ 60 estimated bits (≈ 4 uncommon random words or 16+ random mixed characters), with specific feedback. Tests (`strength.test.ts`) reject `Summer2024!!`, `Liverpool2023`, `P@ssw0rd2024!`, `correct horse battery staple`, `Jennifer1987`, `Tr0ub4dor&3` and others (also before the lists load) and accept four uncommon words and a 16-character random string. SPEC §5 / §8.1 updated.

## Low
- **L1.** Terminal escape injection from the signup note into `journal admin list`. Fix: strip or reject control characters at signup and when printing.
  - **Outcome: FIXED.** Signup rejects C0/C1 control characters (incl. newline, ESC) and bidi formatting characters in the note with `400 invalid_note` (usernames were already restricted to `[a-z0-9._-]`); `journal admin list` replaces control/bidi characters and invalid UTF-8 with U+FFFD. Tests: `TestSignupRejectsControlCharacters`, `TestAdminListSanitises`.
- **L2.** Outstanding recovery tokens are not revoked on recovery-key rotation, passphrase change or reset. Fix: delete the user's recovery_tokens in all three paths.
  - **Outcome: FIXED.** `store.UpdatePassphrase` (passphrase change and recovery reset) and `store.UpdateRecovery` delete all of the user's `recovery_tokens` in the same transaction. Test: `TestRecoveryTokensRevoked`.
- **L3.** TOTP guessing budget is about 720 codes per day. Fix: escalating lockout.
  - **Outcome: FIXED.** Escalating per-account lockout on top of the 5/10 min bucket: the 10th wrong code within 24 h locks TOTP for 1 h, the 20th for 24 h (`429 totp_locked` + `lockedUntil`), for every caller including recognised devices; a correct code resets it. Applies to the sign-in TOTP step and `totp/disable`; the owner can still use a passkey (`passkeyAllowed`) or recovery (recover/verify is only subject to the 5/10 min bucket). Tests: `TestTOTPEscalatingLockout`, `TestLockoutEscalates`.
- **L4.** The PRF wrap can be created without user verification (`evaluatePrf` and registration use 'preferred'). Fix: 'required'.
  - **Outcome: FIXED (frontend).** `evaluatePrf` (the PRF follow-up `get()` that creates the wrap) uses `userVerification: 'required'`, and registration sets `authenticatorSelection.userVerification = 'required'` on the client whatever the server's options say. Passkey unlock and both sign-ins already required UV. (The second-step passkey endpoint also requires UV server-side.)
- **L5.** Browser spellcheck is enabled on the entry body (cloud spellcheckers send text to the vendor). Fix: spellcheck=false on the title and body.
  - **Outcome: FIXED (frontend).** The entry title, the TipTap body (the same editor on desktop and mobile) and image captions set `spellcheck="false"`, `autocorrect="off"`, `autocomplete="off"` and the Grammarly/LanguageTool/Microsoft Editor opt-outs (`data-gramm`, `data-gramm_editor`, `data-enable-grammarly`, `data-lt-active`, `data-ms-editor`); `autocapitalize="sentences"` stays (local only). A new extension detector shows a notice when an extension appears to be active on the page (brief §6).
- **L6.** The combined Markdown export doesn't escape the title or location (`exporter.ts:113-114`). Fix: escapeText.
  - **Outcome: FIXED (frontend).** The combined entry is built by `combinedEntryMarkdown` (`src/export/markdown.ts`): title and location are flattened to one line and escaped like body text (Markdown specials, HTML `<`/`>`, `==`, entity-like `&…;`, and a leading or trailing `#` that would change the heading). Tests: `combinedEntryMarkdown (security review L6)` in `markdown.test.ts`.
- **L7.** The CSP still allows fonts.googleapis.com and fonts.gstatic.com, which are unused. Fix: drop them.
  - **Outcome: FIXED.** CSP is now `style-src 'self' 'unsafe-inline'; font-src 'self'`; `grep -rE 'googleapis|gstatic' backend/web/dist` finds nothing (fonts come from @fontsource). `TestSecurityHeaders` asserts it. SPEC §7 updated.
- **L8.** The systemd unit isn't hardened and runs from the git checkout as the login user. Fix: a dedicated user, a system unit with ProtectSystem=strict, ReadWritePaths, ProtectHome, PrivateTmp, RestrictAddressFamilies and SystemCallFilter, and the binary installed outside the repo.
  - **Outcome: FIXED.** `deploy/journal.service` is now a system unit: `User=journal`, `/usr/local/bin/journal`, `StateDirectory=journal` (0700), `UMask=0077`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp/Devices/Users/IPC`, `NoNewPrivileges`, empty `CapabilityBoundingSet`, `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`, `IPAddressAllow=localhost`/`IPAddressDeny=any`, `SocketBindAllow=tcp:8080`, `SystemCallFilter=@system-service ~@privileged`, `MemoryDenyWriteExecute`, etc. `systemd-analyze security --offline=true deploy/journal.service` → exposure 1.0 "OK". The binary was smoke-tested under the same seccomp/MDWE/address-family/ProtectSystem restrictions via a transient user unit. `deploy/install-selfhost.sh` only builds and prints the root steps (create user, install binary + unit, migrate a `--from DIR` data directory with `sqlite3 .backup` + `secret.key`, owner journal, 0600, Caddy snippet `/etc/caddy/conf.d/journal.caddy` → 127.0.0.1:8080). The user-unit option was dropped.
- **L9.** The README backup recipe creates a world-readable database copy. Fix: umask 077 / mkdir -m 700.
  - **Outcome: FIXED.** README backup recipe runs under `umask 077` with `mkdir -m 700` and 0600 copies; the "Residual risks" section below is now in the README in plain language.

## Residual risks the code can't fix (document in README/About)
- The code is served by this server, so whoever controls the server can ship altered JavaScript.
- The server can withhold, delete or roll back entries, settings and photos, and can pair an old header with a newer body of the same entry (the AAD has no version). It can't read them or move them between entries or users.
- Offline guessing of weak passphrases. The master key is never rotated: anyone who once held the wrapped key and its secret keeps access, even after a passphrase change.
- The recovery key is a single factor for accounts without TOTP (by design: 160 bits).
- Locking doesn't sign you out. The 30-day session cookie has no idle expiry: someone holding it can delete entries or see metadata, but can't read content.
- Metadata: usernames, notes, counts, sizes, timestamps, which photos belong to which entry, IP addresses, IDs.
- Devices that trust Caddy's local root CA trust it for every domain.
- While the journal is unlocked, plaintext sits in the tab's memory. Extensions, the clipboard, print and exports are outside the app's control.
- The first account on a fresh instance becomes admin. Rate limits are in memory.

## Verified correct
No plaintext or keys in network traffic, logs, the database or browser storage. KDF parameters are enforced on both sides. HKDF infos, AAD binding, fresh nonces and non-extractable keys all match the spec. MK lifetime and the idle lock work. Sessions (hashed, rotated, HttpOnly, SameSite=Strict, Secure) are sound. WebAuthn pins origin and RP ID, uses single-use challenges, requires UV at sign-in, and rejects sign-count regressions. TOTP replay is prevented atomically. Authorization is scoped per user. The CSRF check holds on every route. Security headers and body limits are in place. Images are always re-encoded before encryption. Zip-slip isn't reachable. Data files are 0600.
