# Security review: 2026-11-14

Status legend: OPEN → being fixed. Update each item with its outcome when it's fixed.
Backend/deploy outcomes recorded 2026-11-14. Frontend items are added below under "Frontend" with the frontend work.

## Backend

- **B1. Unauthenticated memory exhaustion through concurrent Argon2.** `internal/auth/hash.go` hashed at 19 MiB per call with no cap on how many ran at once; login, sign-up, recovery and reset need no session, and the production machine has 256 MB. A few dozen parallel requests could get the process killed.
  - **Outcome: FIXED.** A process-wide semaphore inside the `auth` package (3 slots) wraps `HashSecret`, `VerifySecret` and `BurnVerify`, so no caller can go around it. A caller that finds every slot taken waits up to 3 s (less if the request's context ends), then gets `auth.ErrBusy`, which `wrap` turns into `503 busy` with `Retry-After: 3`; nothing was checked or changed. `BurnVerify` reports the same error, so known and unknown usernames still answer alike under load. `POST /api/auth/recover/reset` now looks its token up (`store.RecoveryTokenUser`, without spending it) before hashing, so an invalid token costs no Argon2, and a `busy` answer leaves a valid token usable. `GOMEMLIMIT` is set for the deployed process: `160MiB` on the 256 MB production machine, `256MiB` in `deploy/journal.service`. Tests: `TestHashingIsCapped`, `TestHashingQueuesCallers`, `TestBusyHashingIs503`, `TestRecoverResetChecksTokenBeforeHashing`.
- **B2. Brute-force lockouts were memory-only**, and the machine stops when idle, so the escalating TOTP lock (10 wrong codes in 24 h → 1 h, 20 → 24 h) and the five tries per `mfa_pending` session started again from zero on every restart.
  - **Outcome: FIXED for the TOTP lockout and the per-session count; the passphrase counter is unchanged (see below).** Migration `0007_persistent_lockouts.sql` adds `users.totp_fail_count`, `totp_fail_window_start`, `totp_locked_until` and `sessions.mfa_failures`. `auth.Lockout` is now only the rule (window, steps) applied to a stored `LockoutState`; `store.UpdateTOTPFailures` applies it in one transaction, `ResetTOTPFailures` clears it on a correct code, and `store.FailMFASession` counts a session's wrong answers. Status and error codes are the same (`429 totp_locked` + `lockedUntil`, session discarded at the 5th wrong answer). Tests: `TestTOTPLockoutSurvivesRestart` and `TestMFASessionFailuresSurviveRestart` build a fresh server over the same database; `TestTOTPEscalatingLockout`, `TestLockoutEscalates`.
  - **Not changed: the wrong-passphrase buckets** (`passFail`, 30/h per username; `devFail`, 10/h per recognised device) and the 5-per-10-minutes TOTP bucket stay in memory. The passphrase bucket is keyed by username whether or not the account exists, which is what keeps the two indistinguishable at sign-in: storing it only for real accounts would break that, and storing it for every name would let anyone without an account write rows to the database. A restart therefore hands out up to 30 more guesses at a passphrase that is already Argon2id-stretched in the browser, and 5 more at a code, each of which still counts towards the stored lockout. README "Residual risks" says which limits survive a restart.
- **B3. Unbounded sync and list responses.** `GET /api/sync` paged by 100 entries with no byte budget (up to ~75 MB of bodies in memory for one request), `GET /api/entries` loaded every header at once, and a header's ciphertext was only bounded by the 1 MB JSON limit.
  - **Outcome: FIXED.** A change-feed page now ends after 100 entries or before the entry that would take its ciphertext past 4 MiB, always with at least one entry; rows are read one at a time and the scan stops at the cut. The client contract is unchanged (`cursor`, `more`, short pages). `GET /api/entries` keeps its shape (one JSON array, newest first) but is written a page at a time (500 entries or 1 MiB of headers per query, keyset on `(created_at, id)`), so neither the whole list nor a database connection is held while a slow client reads. `header.ct` is capped at 64 KiB on create and update (`413 header_too_large`); the app's headers (title ≤ 300 characters, 160-character snippet, date, place, weather, counts) are well under 1 KB. Tests: `TestSyncPagesByBytes`, `TestChangesSinceByteBudget`, `TestListEntriesStreamsEverything`, `TestEntryHeaderSizeCap`.
- **B4. Admin state-changing routes did not need recent authentication**, unlike changes to one's own credentials: a stolen or unattended admin session could disable, delete or comp accounts and mint invites.
  - **Outcome: FIXED.** `POST /api/admin/users/{id}/{disable,enable,comp,uncomp}`, `DELETE /api/admin/users/{id}`, `POST /api/admin/invites` and `DELETE /api/admin/invites/{id}` are wrapped in `recentAuth` (`403 reauth_required` once the last credential proof is more than 10 minutes old). The admin `GET` routes are unchanged. The app already answers `reauth_required` by asking for the passphrase and retrying. Test: `TestAdminChangesNeedRecentAuth`.
- **B5. Passkey challenge pool denial of service.** The pool held 10,000 challenges and refused new ones (`503 busy`) when full; beginning a sign-in needs no credentials, so anyone could keep it full and block passkey sign-in and registration for everybody.
  - **Outcome: FIXED.** A full pool drops its oldest challenge instead of refusing, and each owner may hold at most 8 outstanding (the client address, IPv6 by /64, for discoverable sign-in; the account for registration and the second sign-in step), the owner's oldest making way. `begin` no longer answers `503`; a dropped challenge's `finish` gets the existing `400 challenge_expired`. Tests: `TestChallengesFullPoolEvictsOldest`, `TestChallengesPerOwnerCap`, `TestPasskeyBeginNeverRefused`.
- **B6. Storage outside the quota.** Passkeys per account were unlimited, and every create/delete cycle left a tombstone row (kept 90 days) that no limit counted.
  - **Outcome: FIXED.** An account holds at most 20 passkeys (`409 passkey_limit` from `register/begin` and, checked in the insert's transaction, `register/finish`). Tombstones are capped at 5000 per user: a deletion past that drops the oldest and raises `tombstone_floor` to the newest one dropped, in the same transaction, exactly as pruning by age does. Deleting is never refused, and a device whose cursor is older than the floor gets the existing `410 cursor_expired` and resyncs from scratch, which is always correct. "No limit when billing is off" is unchanged. Tests: `TestTombstoneCap`, `TestCredentialCap`, `TestPasskeyLimit`.
- **B7. Stripe.** (a) Embedded Checkout loaded `js.stripe.com` into the origin that holds the unlocked journal and widened the CSP for it. (b) Deleting an account left its Stripe subscription running.
  - **Outcome: FIXED.** (a) Embedded Checkout is removed from the server: no `PublishableKey` config, no `publishableKey` in `/api/config`, no `clientSecret` answer, and no `stripeCSP`; the CSP is one constant that names no Stripe origin whatever the configuration. Checkout is always Stripe's hosted page (`{url}`). A request with `embedded: true` (an app loaded before the change) gets `400 embedded_disabled`. `STRIPE_PUBLISHABLE_KEY` is no longer read; the server logs a warning if it is still set. (b) After an admin deletes an account that has a Stripe customer, the server cancels that customer's subscriptions that have not already ended (`billing.Client.CancelSubscriptions`). It is best effort with a 15 s limit: a failure is logged with the customer id for cancelling by hand and does not fail the delete. Tests: `TestBillingNeverAdmitsStripeIntoTheOrigin`, `TestSecurityHeaders`, `TestAdminDeleteCancelsSubscription`, `TestAdminDeleteWithoutBilling`.
- **B8. Supply chain.** CI used actions by movable tag (one of them at a branch head), and the Dockerfile used base images by tag.
  - **Outcome: FIXED.** Every action in `.github/workflows/ci.yml` is pinned to a full commit SHA with its release in a comment (checkout v4.4.0, setup-go v5.6.0, setup-node v4.4.0, cache v4.3.0, and the deploy tool's setup action at a commit of 2026-11-14). The three base images in the `Dockerfile` are pinned by index digest (`node:22-alpine`, `golang:1.27-alpine`, `alpine:3.22`, as resolved from the registry on 2026-11-14). Still unpinned: the deploy tool's binary that its setup action downloads (latest), and the `apk add` packages in the final image. Nothing updates the pins automatically; they need bumping by hand.
- **B9. Fewer dependencies.** `github.com/pquerna/otp` (which pulled in `boombuler/barcode`) and `github.com/google/uuid` were used for a few lines each.
  - **Outcome: FIXED, with one remainder.** TOTP is now stdlib only (`internal/auth/totp.go`: RFC 6238 over RFC 4226, HMAC-SHA1, 6 digits, 30 s, ±1 step, the same unpadded base32 secret and byte-for-byte the same `otpauth://` URL), checked against the RFC 4226 appendix D and RFC 6238 appendix B (SHA-1) vectors and, before the old library was removed, against its output for 2000 timestamps. `internal/uuid` generates v4 ids from `crypto/rand` and parses strictly. `pquerna/otp` and `boombuler/barcode` are gone from `go.mod` and `go.sum`. `google/uuid` is no longer imported by this code but stays as an indirect requirement because `go-webauthn/webauthn` imports it. `fxamacker/cbor` is imported directly only by a test (`passkey_test.go`) and is otherwise a dependency of `go-webauthn`. Path ids are now accepted only in the 36-character form (either case); the braced, `urn:uuid:` and undashed forms the old parser also took are answered `404`. Tests: `TestHOTPRFC4226Vectors`, `TestTOTPRFC6238Vectors`, `TestTOTPSecretForms`, `TestNewTOTPSecret`, `internal/uuid`.
- **B10. Docs said every account needs a second factor.** The code requires one only for admins (deliberate, commit 974d99f).
  - **Outcome: FIXED.** README ("A second factor is optional, except for admins") and SPEC §5 (`DELETE /api/passkeys/{id}`) now match the code. README "Residual risks" gains: signing up reveals whether a username is taken (`409 username_taken`), and which rate limits are in memory.

## Frontend

- **F1. The reload copy of the master key outlived the tab.** `dropForUnload` kept both halves on tab close, browsers restore `sessionStorage` on "reopen closed tab" and session restore, and the only gate was the idle limit read from plain `localStorage` (no limit at all with auto-lock "Never"). Confirmed by hand: closing the tab and pressing Ctrl+Shift+T opened the journal.
  - **Outcome: FIXED.** `local/resume.ts`: the page records `unloadedAt` on `pagehide` (`SessionPersistence.suspend`), and the copy is used only when the navigation type is `reload`, the load starts within 15 s of `unloadedAt`, and the idle limit hasn't passed (bfcache: idle limit only). Anything else deletes the copy. Each unlocked tab holds a Web Lock named after its key; on start every reload key whose lock isn't held is deleted (by age, 1 day, without Web Locks), and `deleteVault` deletes them all. Tests: `local/resume.test.ts`; e2e `start.e2e.ts` "a closed tab that is reopened needs the passphrase". Side effect: typing a URL into an unlocked tab now asks for the passphrase. Residual (documented in README, SPEC §3 and the public DESIGN.md): while unlocked, the reload key and sealed MK are both on disk in the profile.
- **F2. A full resync deleted local entries the server didn't list**, including after an operator restored a backup; and a clean local copy was replaced by whatever the server sent, readable or not.
  - **Outcome: FIXED.** `sync/engine.ts`: when the full pull ends before the cursor the server refused (the server went back in time), nothing is deleted: missing entries are queued again as new, downloaded photos stay on the device. Otherwise (deletion records expired) absence still means deleted. `sync/integrate.ts`: a remote copy that doesn't decrypt never replaces a clean one; ours is queued to repair the server. Tests in `sync/engine.test.ts`.
- **F3. PIN unlock.** The wrap and attempt counter are plain fields in a PIN-locked tab's memory, so anyone with devtools on that tab can guess offline.
  - **Outcome: PARTLY FIXED; rest is inherent.** Nothing in page JavaScript can hide a value from a debugger attached to that page (a non-extractable key can still be *used* from the console), so the proposed extra in-memory wrap was not added. Instead: new PINs are 6–8 digits (existing 4–5 digit PINs still open), and setting or changing a PIN asks for the passphrase. DESIGN.md already says a PIN is a convenience.
- **F4. Embedded Stripe Checkout** ran `js.stripe.com` in the journal's origin.
  - **Outcome: FIXED.** Removed from the client (`billing/Paywall.tsx`, `billing/paywall.ts`); Checkout always opens Stripe's hosted page in a new tab. See B7.
- **F5. Turning sync on wasn't atomic** on the device (settings re-sealed in one transaction, vault linked in another; an interruption after the server signup left the username taken and the journal unlinked).
  - **Outcome: FIXED.** The vault link and re-sealed settings are one IndexedDB transaction. If the username is "taken" by an account that holds this journal's own wrapped key (an earlier attempt cut short), `enableSync` signs in to it and carries on, replacing the never-shown recovery key.
- **F6. Settings could be rolled back by the server** (old PIN, auto-lock "Never", location opt-ins).
  - **Outcome: FIXED.** Settings carry a change counter `n`; a device refuses a server copy that doesn't decrypt or is older than its own and pushes its own back. Test in `sync/engine.test.ts`. **Not changed:** `/api/me` still overwrites the device's passphrase wrap unverified. Checking it needs the passphrase, and keeping the old wrap as a fallback would let an old passphrase keep working on that device; the server can only break offline unlock this way, not learn anything.
- **F7. A local journal could get a new recovery key or PIN without the passphrase.**
  - **Outcome: FIXED.** `checkLocalPassphrase` (unwraps the device's wrapped MK) gates `regenerateLocalRecovery` and PIN setup.
- **F8. Passkey sign-in with PRF took `userVerification` from the server.**
  - **Outcome: FIXED.** `toRequestOptions` always sets `required`.
- **F9. Smaller items.** Markdown export wrote link hrefs without a scheme check; `authKey` wasn't zeroed on some error paths; a burned entry could reappear if the server served it again.
  - **Outcome: FIXED.** Export links are http/https/mailto only. `authKey` is zeroed in `finally` in login, recovery verify and reset. A burned entry's outbox record stays as a marker after it is sent; if the entry arrives again it is refused and deleted on the server again.
- **F10. Dependencies.** `fflate` and `qrcode` replaced by `export/zip.ts` and `lib/qr.ts` (`qrcode` stays as a devDependency: the tests compare every version 1–40 and all 8 masks module for module); unused `@tiptap/extension-bubble-menu` dropped. `npm audit` advisories in `@tiptap/core` 2.x and `react-router` remain (not reachable; see the review). The client retries `503 busy` (B1) twice.
